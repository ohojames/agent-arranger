# 6. รูปแบบการรายงานผล (บังคับทุกครั้งที่จบงาน)

ตอบเป็นภาษาไทย โค้ด คอมเมนต์ และชื่อตัวแปรเป็นภาษาอังกฤษ

รายงานผลเป็น Executive Summary **สามหัวข้อ ตามลำดับนี้เท่านั้น**

## 1. สถานะปัจจุบัน

เสร็จหรือไม่เสร็จ ใช้ได้หรือใช้ไม่ได้ พร้อมคำอธิบายที่สั้นที่สุด
**ยาวได้ไม่เกินสองสามบรรทัด** รายละเอียดไปอยู่หัวข้อ 2 และ 3

## 2. สิ่งที่ทำไปแล้ว

สิ่งที่ทำสำเร็จจริง พร้อม**ผลรันที่ยกมาแปะ** ไม่ใช่คำบรรยาย

## 3. สิ่งที่ยังไม่ได้ทำ และข้อเสนอว่าควรทำต่อ

สิ่งที่เหลือ **พร้อมข้อเสนอว่าควรทำอะไรต่อ** ไม่ใช่แค่ลิสต์ช่องว่าง
อะไรที่มาอยู่ตรงนี้เพราะทำอัตโนมัติไม่ได้ ต้องบอกตรงๆ ว่าเพราะอะไร

## กฎการเขียน

- ขึ้นต้นด้วยคำตัดสิน ไม่ใช่เล่ากระบวนการ — "เสร็จ พร้อมใช้" มาก่อนรายละเอียด
- **ข้อมูลที่เทียบกันได้ตั้งแต่ 3 รายการขึ้นไป ต้องเป็นตาราง** ห้ามเป็น bullet ยาว
- ห้ามเล่าว่างานดำเนินไปยังไงตามลำดับเวลา ผู้ใช้อ่านผลลัพธ์แล้วตัดสินใจ
- ไฟล์ที่อ้างถึง ให้เขียนเป็น markdown link ที่คลิกได้ พร้อมเลขบรรทัดถ้ามี
- คำสั่งที่ผู้ใช้อาจต้องรัน ให้ใส่ใน code block ภาษา `bash` แยกก้อนละหนึ่งคำสั่ง

# 7. ทำเองให้จบ อย่าโยนขั้นตอนกลับไปให้ผู้ใช้

ถ้าทำเองได้ ให้ทำ อย่าเขียนคู่มือให้ผู้ใช้ไปกดเอง
สิ่งที่ทำเองไม่ได้จริงๆ ให้ไปอยู่หัวข้อ 3 พร้อมเหตุผลว่าทำไมถึงทำไม่ได้

# 8. ข้อจำกัดของ Windows (เครื่องนี้)

- `npx` `npm` และ `.cmd` shim อื่นๆ spawn ตรงๆ ไม่ได้ ต้องผ่าน shell
  หรือเรียก JS entry point ของ package ผ่าน `node` แทน
- heredoc ทำให้ backslash เพี้ยน — regex และ path ของ Windows ให้เขียนด้วย
  เครื่องมือแก้ไฟล์ ไม่ใช่ pipe สคริปต์เข้า bash
- ตั้ง `PYTHONIOENCODING=utf-8` ก่อนรัน Python ที่พิมพ์ภาษาไทย
- ไฟล์ต้นฉบับอาจเป็น UTF-16 ให้อ่านแบบเผื่อไว้แล้วแปลงเป็น UTF-8
