# 3. ลำดับการทำงาน: คิด → ทำ → ส่ง

ห้ามข้ามขั้น และห้ามเริ่มที่ "ทำ"

## คิด (ก่อนเขียนโค้ดบรรทัดแรก)

ทำเมื่อผู้ใช้ขอ "เพิ่ม / สร้าง / ทำ / ออกแบบ / ปรับ" อะไรที่ยังไม่มี

- ระบุสมมติฐานออกมาเป็นข้อๆ ถ้าไม่แน่ใจให้ถาม อย่าเดาเงียบๆ
- ถ้าตีความได้หลายแบบ ให้เสนอทุกแบบ อย่าเลือกเองแล้วเงียบ
- ถ้ามีทางที่ง่ายกว่า ให้พูด แม้ผู้ใช้จะไม่ได้ถาม
- งานที่มีหลายขั้น ให้เขียนแผนสั้นๆ ก่อน พร้อมวิธีตรวจของแต่ละขั้น:
  `1. [ทำอะไร] → ตรวจด้วย: [คำสั่ง/สิ่งที่ต้องเห็น]`

## ทำ

### 3.1 แก้บั๊ก = เริ่มที่ test ที่ fail เสมอ

เขียน test ที่ reproduce บั๊กให้เห็นก่อน แล้วค่อยแก้ให้มันผ่าน
ถ้าไม่มี test ที่ fail ก่อน แปลว่าไม่รู้ว่าแก้จริงหรือแค่ย้ายปัญหาไปที่อื่น

### 3.2 แก้ให้ครบทุกจุดที่เป็นคู่กัน (สำคัญที่สุด)

ความผิดพลาดที่เกิดบ่อยที่สุดคือ "แก้หน้า เพิ่ม แต่ลืมหน้า แก้ไข และหน้า ดู"

ก่อนบอกว่าเสร็จ ต้องไล่รายการนี้ทุกข้อ และรายงานว่าแต่ละข้อแตะหรือไม่แตะ เพราะอะไร:

| ถ้าแก้สิ่งนี้ | ต้องไปดูด้วยว่าต้องแก้ไหม |
|---|---|
| เพิ่ม/แก้/ลบ field | form เพิ่ม, form แก้ไข, หน้า detail/view, ตาราง list, ตัวกรอง, export, PDF/print, validation, type, ตัว map ข้อมูลฝั่ง API |
| แก้ API route | ทุกหน้าที่เรียก route นั้น, type ของ response, การจัดการ error, permission/สิทธิ์การมองเห็น |
| แก้ schema ฐานข้อมูล | migration, type, repository, ทุก query ที่ select คอลัมน์นั้น, คอลัมน์ที่บางบทบาทห้ามเห็น |
| แก้ permission | API, UI ที่ซ่อนปุ่ม, และ **ข้อมูลที่ส่งออกจาก server** — ห้ามส่งคอลัมน์ที่บทบาทนั้นห้ามเห็นออกจาก server เด็ดขาด |
| แก้ component ที่ใช้ร่วม | ทุกที่ที่ import มันไปใช้ |

วิธีไล่ให้ครบ: ค้นด้วยชื่อ symbol ไม่ใช่ข้อความ และค้นทั้ง re-export กับ alias ด้วย
ใช้ `grep -rn` (หรือเครื่องมือ Grep) ค้นหลายคำ (ชื่อ field, ชื่อ type, ชื่อคอลัมน์ใน DB, ชื่อ label ภาษาไทย)

### 3.3 แตะเท่าที่จำเป็น

- ห้าม "ปรับปรุง" โค้ด คอมเมนต์ หรือ format ที่อยู่ข้างๆ แต่ไม่เกี่ยวกับงาน
- ห้าม refactor สิ่งที่ไม่ได้พัง
- ทำตามสไตล์เดิมของไฟล์ แม้จะไม่ใช่สไตล์ที่ตัวเองชอบ
- เจอ dead code ที่ไม่เกี่ยว ให้บอก อย่าลบเอง
- ลบเฉพาะ import/ตัวแปร/ฟังก์ชันที่ **การแก้ของตัวเอง** ทำให้ไม่ถูกใช้แล้ว

เกณฑ์ตรวจ: ทุกบรรทัดที่เปลี่ยน ต้องชี้กลับไปที่สิ่งที่ผู้ใช้ขอได้

### 3.4 เขียนให้น้อยที่สุดที่แก้ปัญหาได้

ไม่มีฟีเจอร์ที่ไม่ได้ขอ ไม่มี abstraction สำหรับของที่ใช้ที่เดียว
ไม่มี "ความยืดหยุ่น" ที่ไม่ได้ขอ ไม่มี error handling สำหรับเคสที่เป็นไปไม่ได้
ถ้าเขียนไป 200 บรรทัดแล้วมันควรเป็น 50 ให้เขียนใหม่

## ส่ง

### 3.5 ห้ามพูดว่า "เสร็จ" โดยไม่มีผลรันมาแปะ

รันคำสั่งที่จะจับความพังได้จริง แล้วยกผลลัพธ์มาให้ดู

| งาน | คำสั่งที่ต้องรัน |
|---|---|
| โปรเจกต์ TypeScript | `npx tsc --noEmit` แล้วตามด้วย build จริง |
| อะไรที่ deploy แล้ว | ยิง URL จริง แล้วรายงาน status code |
| เปลี่ยนข้อมูล | อ่านแถวกลับมาเทียบกับที่ตั้งใจ |
| สคริปต์ที่เขียนไฟล์ | เปิดไฟล์ตัวอย่างกลับมาดูว่ายัง parse ได้ |
| UI | เปิดหน้าจริงดู (ดูข้อ 4) |

ถ้าไม่ได้รันตัวไหน ให้บอกว่าตัวไหนและเพราะอะไร
คำว่า "น่าจะใช้ได้" ไม่ใช่การรายงานผล

### 3.6 ห้าม fallback เงียบๆ

ถ้าทางที่ตั้งใจไว้ล้มเหลวแล้วไปใช้ทางที่ด้อยกว่า — mock แทนของจริง,
list ว่างแทน error, cache แทนต้นทาง — **ต้องบอกในผลลัพธ์**
ผลสีเขียวที่ได้มาด้วยวิธีอื่น คือการรายงานที่บิดเบือนสิ่งที่ตรวจไปจริง

### 3.7 ตัวเลขที่คำนวณได้ คือข้อกล่าวอ้าง จนกว่าจะตรวจตัวตั้ง

ก่อนโชว์อัตราส่วน เปอร์เซ็นต์ หรือตัวเลข coverage ให้ถามว่าตัวหารมีอะไรอยู่บ้าง
และของทุกชิ้นในนั้น *มีโอกาส* เข้าเงื่อนไขไหม
ถ้าผู้ใช้ทักตัวเลข ห้ามอธิบายสูตรจากความจำ ให้คำนวณใหม่จากข้อมูลต้นทางแล้วโชว์แถว

# 4. ความปลอดภัยของข้อมูล (ห้ามฝ่าฝืน)

- ห้ามรันอะไรที่ truncate / delete / ล้างตารางในฐานข้อมูลจริง
- ห้ามลบบัญชีผู้ใช้ หรือเขียนทับข้อมูลธุรกิจแบบ bulk
- การแก้ข้อมูลต้องเป็น insert/update ทีละรายการที่ปลอดภัยเท่านั้น
- ก่อนลบหรือเขียนทับอะไร ให้เปิดดูของเดิมก่อนเสมอ
